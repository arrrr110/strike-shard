## 归属方（Owner）

一局的双方各是一个**归属方**。归属方是比回合并寿的状态，持有血量池。

| 项 | 结论 |
| --- | --- |
| 数量 | 两个：我方（`owner_id = 0`）/ 敌方（`owner_id = 1`） |
| 血量池 | **99 点**（占位值，由用户在编辑器里试） |
| 归零后果 | **对局结束，该方失败** |
| 一期的敌方 | **bot**。需要一个简单的决策机制（见"待定"） |
| 二三期的敌方 | 可以是其他玩家（联机）。**现在不设计**，但见下面的硬约束 |

**联机现在不做，但有一条现在就要守住的约束：确定性。**
二期要支持人类对手，意味着这套规则必须能在两端算出同样的结果——
固定物理步长、不依赖渲染帧、事件可序列化回放。本项目现在的
`--headless --fixed-fps 60` 探针做法正好是友好的，**不要引入只在客户端算的东西**
（随机数要显式播种、不要用真实时间做判定）。现在破坏它，二期要重写。

## 角色（上场角色）

| 项 | 结论 |
| --- | --- |
| 上场数量 | 每方 **3 个**（初定） |
| 能否被摧毁 | **不能**。角色永不退场 |
| 血量下限 | 0。到 0 后成为**薄弱点**（见下） |
| 薄弱点能力 | **仍然全功能可用**——可被选中、可发射、控制域照常参与围攻判定 |
| 薄弱点的代价 | 它在碰撞中受到的伤害**全部转移给归属方**（不再是"只溢出超出部分"） |

**为什么要设薄弱点这一档**：它把"角色被打空"从一个退场事件变成了一个**持续的战略负债**。
玩家不会因为角色被打空而少一个棋子，而是多了一个"每次被碰都会让自己掉血"的包袱，
于是有了"保护己方低血角色"这件事。这也是"角色不可摧毁"能成立的前提。

（2026-10-10 决定：角色不死亡的设定在此细化为"薄弱点"。）

## 角色类型与克制【暂时屏蔽】

> ⚠️ **2026-10-10 决定：类型克制先屏蔽，以后再实现。**
> 当前 `atk` 直接就是伤害，`role_type` 对数值没有任何影响。
> 保留 `role_type` 字段与调用点，重新启用只需改 `player.gd` 的 `damage_multiplier_against()`。
> 下面是启用后的规则。

| 类型 | 颜色 | 英文 | 克制关系 |
| --- | --- | --- | --- |
| 护卫 | 红 | Protector | 克 斗士 |
| 斗士 | 绿 | Fighter | 克 施法者 |
| 施法者 | 蓝 | Caster | 克 护卫 |

- 三角循环：**红 > 绿 > 蓝 > 红**
- 克制方向**伤害翻倍**；被克制方向目前**不设减伤**（只有翻倍，没有减半）
- **召唤物无属性**，不参与克制关系

**视觉落地（2026-10-10 决定）**：
- **选中描边改为中立的白色**（原为绿色，与斗士的绿撞车）——已落地
- **类型用贴图区分**，不走染色——待美术资源接入

> 附带好处：类型不用染色，就不需要改 `aura.gdshader` 那个"覆写 COLOR、吃掉 modulate"的问题。
> 但如果以后要给棋子染队伍色，那个 shader 还是得先改。

## 血量模型

两套血量，不可互相代替，界面上也是两个不同的显示区域：

### 角色血量（`hp` / `max_hp`）

- 下限为 **0**，不会为负
- **归零即成为薄弱点**，但角色不退场

### 归属方血量（owner HP）

- 一方的总耐久池，**99 点**
- 归零 → **对局结束，该方失败**

### 伤害的去向

一次伤害 `D` 打到剩 `H` 点血的角色身上：

| 情形 | 角色承受 | 归属方承受 |
| --- | --- | --- |
| `H > 0` 且 `D ≤ H` | `D`（血量降为 `H - D`） | 0 |
| `H > 0` 且 `D > H` | `H`（血量降为 0，成为薄弱点） | `D - H` |
| `H == 0`（已是薄弱点） | 0 | `D`（全额转移） |

第三行是薄弱点的定义，也是它与"普通溢出"的唯一区别。

## 伤害公式

**伤害 = 攻击方 `atk`。碰撞速度不参与。**（2026-10-10 决定）

- **类型克制暂时屏蔽**，所以现在**没有倍率**：`伤害 = atk`。
  启用后才有"克制方向 ×2"。见上节。
- 召唤物无属性，永远不吃克制、也不触发克制

> ⚠️ **这条决定的连锁后果，必须说清楚**：蓄力只决定**射程与落点**，不决定伤害。
> 蓄力条的几何预测依然成立（末端仍是球停下的地方），但它**不再预测伤害**——
> 全力一撞和轻碰一下，只要撞到同一个角色，伤害完全一样。
> 蓄力的意义从"打多疼"退化成"打到谁、打几个"。
> 若以后觉得这个退化不可接受，改法是回到"atk 为基、速度调制"，见"待定"。

**碰撞伤害是双向的**：碰撞双方**各打出自己的 `atk`**，互相扣血。
不是"撞的一方打人、被撞的一方挨打"。（2026-10-10 用户确认。）

**只有 ZOC 结算是单向的**：围攻成立时只有被围方受伤，围攻方不掉血（见下）。
其余场合（碰撞）都是双向。

> 实现备忘：现在 `atk` 是 10、`max_hp` 是 70（全员统一占位值），
> 所以一次碰撞双方各掉 10 血。先前用 30/40 时一撞掉掉四分之三血，手感像"两边都在挨打"。

## 召唤物

| 项 | 结论 |
| --- | --- |
| 来源 | 角色的能力产生（属卡片/技能模块，本模块只定义它是什么） |
| 形态 | **实体棋子**（`RigidBody2D`），和角色一样参与物理与碰撞 |
| 能否被摧毁 | **能**。血量归零即从棋盘移除——这一点与角色相反 |
| 属性 | **无属性**，不参与类型克制 |
| 数量上限 | **「召唤物 + 角色」合计每方上限 7**。角色固定 3 个且不可摧毁，所以**召唤物最多同时存在 4 个**。再生成时**最早的那个召唤物自动销毁**（FIFO，角色永不参与顶替） |
| 生成位置 | 默认在**执行角色的左边** |
| 归属 | 属于召唤它的角色所在的归属方 |

**召唤物一出现，就对回合机制提出两条硬要求**（见 [回合机制技术方案](../10-turn/DESIGN.md)）：

1. **棋子名单会在对局中变化。** 回合机制原先假设名单恒定（"角色永不退场"），
   现在不成立——静止判定必须在召唤物生成/被摧毁/被顶替后立刻看到新名单。
2. **不能在物理回调里直接释放刚体。** 摧毁一个正在参与碰撞的 `RigidBody2D` 必须延迟到物理步之后。

**FIFO 顶替还需要一张按归属方分组的登记表**：上限要求知道"哪个是最早的"，
所以每个 owner 要维护一份**有序**的召唤物清单。这张表和上面第 1 条是同一套数据结构
——一旦有它，静止判定的名单刷新也就有地方挂了。

**为什么把角色也算进上限**：7 是**棋盘上属于这一方的实体总数**，不是"召唤物配额"。
角色占掉 3 个固定名额且永不释放，所以实际留给召唤物的只有 **4** 个。
好处是"一方最多在场上堆多少东西"只有一个数字，不用把角色数和召唤物数各记一遍。
若以后上场角色数改了（例如改成 4 个），召唤物空间会**自动**变成 3 个，不需要另立规则。

> 边界情形：万一某方的角色数本身就达到 7，则召唤物没有空间、也没有可顶替的对象
> （角色不可销毁）。当前角色数固定 3，不会发生；如果以后角色数可配，这里要加一条拒绝规则。

> 性能影响：每方 ≤ 7、双方合计 **≤ 14 个物理实体**（原红线是"单场角色数 ≤ 10"）。
> 已按新规模更新 [全局约束](../00-overview/constraints.md)。

## 属性契约

| 字段 | 含义 | 谁用 |
| --- | --- | --- |
| `owner_id` | 归属方（`0` = 我方，`1` = 敌方） | 操作许可、围攻判定、伤害去向 |
| `atk` | 攻击力 | 伤害结算 |
| `hp` / `max_hp` | 角色血量，下限 0 | 结算、薄弱点判定 |
| `kind` | 角色 / 召唤物 | 能否被摧毁、是否参与克制 |
| `type` | 护卫 / 斗士 / 施法者 / 无属性 | 克制判定 |
| `zoc_radius` | 控制域半径（像素） | 覆盖查询 |
| `card_index` | 对应卡片序号 | **仅用于定序**，由内容层提供 |
| `mounted_skills` | 挂载技能 id 列表 | 见 [待设计](../90-todo/character-mounted-skills.md) |

> **`controllable` 已退役（2026-10-10 落地）。** 它原先同时承担两件事——
> "这枚是谁的"（我方 = `true`，敌方 = `false`）和"我能不能操作它"。
> 现在归属由 `owner_id` 回答，能不能操作由阶段机按阶段发放
> （[回合机制技术方案](../10-turn/DESIGN.md) 决策 11）。
> 不拆开的话，二期接入人类对手时"敌方是另一个玩家"会无处安放。

## 待定（需要另行设计）

- **角色池**：有哪些角色、各自的数值、专属效果、类型分布。
- **伤害数值细节**：`atk` 10~70 的具体分布；一次碰撞是否只结算一次（连锁碰撞会结算多次吗）。
- **双向伤害是否真的各打各的**：**已确认（2026-10-10）——碰撞双方各打出自己的 atk，互相扣血。**
- **~~ZOC 的单双向边界~~**：**已确认（2026-10-10）——整个 ZOC 结算都是单向的**
  （只有被围方受伤，围攻方不掉血）。文档原先写的"未成围攻时双向交换"**作废**。
- **召唤物**：生成位置被占或落在棋盘外怎么办；数量上限；是否随回合消失；能否被选中发射。
- **薄弱点是否可被选中发射**：已定"全功能可用"，但发射一个薄弱点意味着主动把风险送出去，
  这是不是想要的战术（还是有意的惩罚）。
- **bot 决策机制**：一期要实现。形态（规则式 / 评分式）、决策粒度（选哪个角色 / 瞄哪里 / 蓄多少力）。
- **控制域半径的具体像素值**：由用户在编辑器中试出手感。
- **角色的"朝向"是否有规则意义**（目前贴图倾斜只是视觉表现）。
- **专属卡与角色的绑定关系。**
- **要不要回到"atk 为基、速度调制"**：如果实测下来"蓄力不影响伤害"手感不对，这是回退点。
