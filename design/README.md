## 文档约定

- 目录与文件名用英文 slug（跨脚本/工具安全），正文用中文。
- 编号前缀表示阅读顺序，间隔 10，便于日后插入新模块。
- 状态标记：`骨架`（只有边界与待定项）/ `编写中` / `已定稿`。
- 决策必须进「已确认的关键决策」表并注明日期。被推翻的决策**不删除**，
  在原处标注修订（保留决策演变史，避免同一个问题被反复讨论）。
- **描述尚未实现的东西时必须显式标注**（【未实现】/「设计储备」）。文档读起来像现状、
  实际一行代码都没有，是这套文档最容易出错的地方。

## 与 ravenspec 的分工

> **`ravenspec/` 目录当前已从仓库删除**（commit `f33c0be`，2026-10-10）。
> 下面的分工是它恢复后的约定，先留着。

- `design/<module>/`：**长期活文档**。模块需求（PRD）与技术方案（DESIGN）都迭代在这里。
- `ravenspec/changes/<change>/`：**单次变更**的工作区。放 spec delta 与 TASK。
- 变更落地后，spec delta 归档进 `ravenspec/specs/<capability>/`。

因此本项目的 PRD 按模块存放在 `design/` 下，SDD 工作区只管 spec 与 TASK。
这样"实现依据"可回溯，"模块需求"又不被单次变更的边界切碎。

## 冲突处理

同一件事可能出现在两处：`design/`（要什么、怎么做）与代码。
两者冲突时：

1. 代码与文档不符时，**先判断谁是错的**——手感类结论以用户在编辑器中的实际行为为准。
2. 判断的结果必须落到某一侧并同步另一侧，不允许长期不一致。
3. 决策被推翻时保留原始主张与修订原因（见上面的文档约定）。
