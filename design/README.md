## 与 ravenspec 的分工

- `design/<module>/`：**长期活文档**。模块需求（PRD）与技术方案（DESIGN）都迭代在这里。
- `ravenspec/changes/<change>/`：**单次变更**的工作区。放 spec delta 与 TASK。
- 变更落地后，spec delta 归档进 `ravenspec/specs/<capability>/`。

因此本项目的 PRD 迁到 `design/` 下按模块存放，`ravenspec/changes/<change>/PRD.md`
原位置只留一个指针文件，SDD 工作区只管 spec 与 TASK。这样"实现依据"可回溯，
"模块需求"又不被单次变更的边界切碎。

## 文档约定

- 目录与文件名用英文 slug（跨脚本/工具安全），正文用中文。
- 编号前缀表示阅读顺序，间隔 10，便于日后插入新模块。
- 状态标记：`骨架`（只有边界与待定项）/ `编写中` / `已定稿`。
- 决策必须进「已确认的关键决策」表并注明日期。被推翻的决策**不删除**，
  在原处标注修订（保留决策演变史，避免同一个问题被反复讨论）。

## 冲突处理

同一件事在三处出现：`design/`（要什么、怎么做）、`ravenspec/specs/`（可验证的行为）、
代码。三者冲突时：

1. 以 `design/` 为准，同步修订 spec；
2. 修订 spec 时保留原始需求块的痕迹（在变更记录里注明原主张与修订原因）；
3. 代码与文档不符时，**先判断谁是错的**——手感类结论以用户在编辑器中的实际行为为准。
