# 棋盘元素与数字可读性

> 模块：`50-presentation` ｜ 状态：**设计，未实现** ｜ 最近修订：2026-10-13
>
> 这一篇服务于两件事：把棋盘补成**特效载体**，把散落的数字**收成一套系统**。
>
> **分工**：棋盘节点与美术由**用户在编辑器里搭**；数字系统由 Agent 实现，
> 样式参数全是导出项，最终手感归用户在编辑器里定。

## 一、特效载体需要的不是美术，是**层次与落点**

特效做不出来，通常不是素材不够，是**没有地方放**。现在这些东西挤在世界坐标里、
各自为政：`ColorRect` 当棋盘、空 TileSet 的 `TileMapLayer`、棋子散在 `StaticBody2D` 下、
ZOC 圈与血量字是 `hp_overlay._draw` 直接画出来的。特效加进去会跟它们打架
（谁在上面、谁跟着相机抖、谁该被挡）。

**建议的分区**（节点名随你，重点是分区本身）：

```
main
├── ShakeCamera                      相机：抖的是它
├── World (Node2D)                   ← 世界坐标层，**跟着相机一起抖**
│   ├── Background                     背景 / 地面        z 最低
│   ├── Board                          棋盘、边框、四壁   ← 四壁现在是看不见的物理体
│   ├── Pieces                         棋子
│   ├── Vfx            ✨这一层最值得先加   **所有世界特效的落点**
│   └── Debug                          调试绘制（ZOC 圈、血量字），最终会被替代
└── UI (CanvasLayer)                 ← 屏幕层，**不跟着抖**
```

**为什么先加那个空的 `Vfx`**：将来时间线发一个事件，得有个明确的地方接住它。
没有它，每个特效会各自找爹（有的挂相机下、有的挂棋子下、有的挂场景根），
半年后就没人说得清哪个特效在哪一层。**空着不花钱，但没有它，落点就永远是随机的。**

「谁在世界层、谁在 UI 层」这条分界线不是新规矩 —— 加相机时就立过了
（世界坐标的东西跟着抖，屏幕 UI 不跟着），这里只是把它**固化进场景结构**。

## 二、要补齐的元素（按"能承载什么特效"排，不按美术分类）

| 元素 | 补它的理由（不是"好看"，是"特效需要它"） |
| --- | --- |
| **背景** | 特效的对比底。亮特效要有暗底才亮得起来 —— 现在整个背景是默认灰 |
| **棋盘边界 / 边框（四壁）** | 球撞墙是这套玩法的核心反馈之一，**但四壁现在完全看不见**。撞击特效、墙面高光、边界提示都无处依附 |
| **地面材质 / 网格** | 位移与 ZOC 圆需要**参照物**才读得出距离。没有地面细节，"球飞了多远"是感觉不到的 |
| **棋子底座 / 阴影** | 多个数字同时出现时，"这个数字属于哪一枚"要靠底座定位 |
| **归属与类型的视觉区分** | 现在六枚共用同款贴图 + 头上的小字。归属一眼不可辨，特效的配色就没有锚点 |
| **ZOC 圆的正式形态** | 现在是 `_draw` 画的调试圈。它是这套玩法的核心机制，最终得是美术 |
| 归属方血量（胜负条件） | 现在只是左下角一行小字，而它是**输赢本身** |

> 可用的素材：`dodge_the_creeps_2d_assets/Tiny Swords (Update 010)/` 下有
> `Terrain` / `Deco` / `Effects` / `Factions` / `UI` / `Resources` 六类。

## 三、数字系统

### 现状：数字散在三处，各画各的

| 数字 | 现在在哪 | 画法 |
| --- | --- | --- |
| 棋子血量 / 类型 / 攻击力 | `hp_overlay.gd` | `_draw` + `ThemeDB.fallback_font` |
| 归属方血量池 | `main.tscn` 的 `UI/OwnerHp` | 裸 `Label` |
| 伤害数字 | **不存在** | — |

**参考炉石的第一步不是"做得像"，是"把它们收成一套"** —— 同一套字体、同一套描边、
同一套颜色语义、同一条位置规则。否则会得到三种风格。

> 顺带澄清一条旧待办：`TODO.md` 第 1 条问的是"攻血**数值**该不该搬进 Player 节点" ——
> 那个答案是**不用**（真相来源已经在 `player.gd`）。
> 而这里说的是**呈现**该不该收成一套 —— 那个答案是**该**。同一件事的两个面，不矛盾。

### 四条可执行的规则（参考炉石的做法，素材自己做）

1. **描边是命根子。** 深色描边 + 浅色字身。没有描边的数字在花哨背景上根本看不清，
   这是所有数字的第一条要求，比字体选什么重要得多。
2. **颜色语义固定，且只用一套**：伤害=红、治疗=绿、增益=黄/白。玩家学一次就永远知道。
3. **数字要"弹"和"先慢后快"**：弹出时先超过 1.0 再回落（pop），上飘 30–60 px，
   **前段慢、后段加速淡出**。匀速上飘看起来是"飘"，不是"打出来"。
4. **同帧多个数字必须错开**：横向错开 + 时间错开。

### 我们特有的难点：一次发射可能结算两次

第 4 条对我们是**刚需**，不是锦上添花：一次发射可能结算两次伤害
（满蓄力时是常态 —— 被撞的会撞墙折返再撞回行动角色，见
[DESIGN.md](../10-turn/DESIGN.md) 的「一次发射可能结算不止一次」）。
所以"多个数字叠在一起"不是边界情况，是常规情况。

### 工程约束

本项目跑在 **`gl_compatibility`**（本机 MoltenVK 建不出 Forward+ / Mobile 的计算管线，
见 [全局约束](../00-overview/constraints.md)）。选素材与做法时要在它的能力范围内：

- **稳**：贴图序列帧、`Sprite2D` 拼接、`CanvasItem` 着色器、`_draw` 程序化绘制
- **谨慎**：重量级 GPU 粒子（`GPUParticles2D` 在 gl_compatibility 下能力受限）

## 四、落地顺序

1. **用户在编辑器里**：按上面的分区补棋盘元素（背景 → 边框 → 地面 → 底座 → 归属区分）
2. **Agent**：实现数字系统（一套样式 + 弹出动效 + 错开规则），参数全部导出
3. **顺带还一笔债**：伤害数字落地时，把屏幕抖动从"临时直连"收编成正式的 `hit` 标记
   （见 [时间线](timeline-and-markers.md)）
