# 开发过程架构内聚/耦合备忘录

## 用法（2026-10-13 定）

目的是维持工程结构合理、降低模块耦合，避免代码熵增到后期难以理解。

**铁律：每一条待办都必须挂一个「逼它出来的功能」。** 挂不上的就是伪待办，删掉 ——
没有需求在逼的"看起来不优雅"不是债，留着只会让人在错的地方花时间。

起新需求时对一次账（见 [AGENTS.md](../AGENTS.md) 的「熵账本与架构对账」）：
这次逼出了哪条旧债？会不会制造新的中间产物？同一个概念这次碰了几处？

## 「探讨」

1. ~~攻击力/血量显示是否需要整合至 Player 节点~~ —— **已判定：不用做（伪待办，2026-10-13）**。
   数值本身住在 `player.gd`（`atk` / `max_hp` / `role_type`），`hp_overlay` 只是**读**它画字，
   **真相来源只有一个**，不存在双份。而且文档已写明它是调试级、最终会被删掉。
   它的时机是**用户在编辑器里做正式血条**的那天，不是现在。

2. **Player / Mob 是否需要继续抽象合并为同一父类**
   - 现状：**脚本早就合一了** —— `mob.tscn` 挂的就是 `player.gd`，只覆盖 `owner_id = 1`。
   - 剩下的两个真实缺口：(a) `player.gd` 这个名字名不副实（它其实是棋子基类）；
     (b) 两个 `.tscn` 里重复的物理配置。
   - **逼它出来的功能：召唤物**（决策 27）。那是第三种棋子，会真正逼出"三类共用一套物理/表现，
     但生成与寿命不同"。(a) 可以包在任意一个碰到 `.tscn` 引用的 spec 里顺手做。
   - bot 落地时会先复核一次这条：敌方棋子被发射时用的接口必须和玩家一致。

3. **未来可能需要一个回合控制器（controller）作为总线，当前 game_flow 节点只是中间产物**
   - 现状：`game_flow.gd` **754 行 = 全项目 44%**，一个人管 6 件事（阶段机 / 碰撞结算 /
     ZOC 结算 / 碰撞冻结 / 归属方血量 / UI 刷新），"卡牌装载"还留着一个空分节等着塞进去。
   - **逼它出来的功能：卡牌装载（环节 1）。** 那时它会再吃进"出牌 / 装载"两个入口。
   - **做法：不是"先拆再写卡牌"，而是把"拆 game_flow"当成卡牌 spec 的一部分** ——
     这样拆分有明确的验收标准（卡牌装载能不能干净地落进去），而不是无限的。

4. **联机确定性收口**（2026-10-15 起意，**尚未动手**）
   - **已做对的部分比想象中多**：伤害是属性算的（决策 24，速度不参与）、结算走事件、
     表现有排空闸门、冻结本身就是一个天然的"逻辑时刻"锚点。
     **联机最难的部分无意中已经做对了**，剩下的是收口，不是重构。
   - **已收口**：bot 随机源 → 可注入种子的伪随机（决策 40）。
   - **已知未收口**（都还没做，等联机需求真来）：
     - `_impact_pending` 攒的是**节点引用**，过不了网线 → 要换成稳定的 piece 标识
     - `_end_freeze()` **既解冻又结算**，耦合在一处 → 联机时要能"只结算不解冻"
     - 物理参数散在各 `@export` 里 → 两端必须同参，要有一个集中出处
     - `FREEZE_DELAY_STEPS = 3` 是**引擎实现细节**（实测冲量延后 2 步落地）→ 要当"协议"记录假设
   - **逼它出来的功能：联机对战。** 在那之前上面四条都是伪待办，**不要动**。
   - **架构方向**（已想清楚，联机真来时直接用）：**物理当表现，事件当真相** ——
     权威方跑物理产出碰撞事件集；双方各自跑物理只为表现流畅；结果以事件集为准，
     每次"排空"时刻对齐，不一致就末态硬校正。回合制独有红利：**一杆结束时全场静止，
     末态校正看不出来**（实时游戏拿不到这条）。
   - **不上 lockstep / rollback**：`PhysicsServer2D` 没有手动步进接口
     （见 [constraints](00-overview/constraints.md) 的引擎事实），"按需重算 N 帧"做不到。
     自己写定点数物理的成本在这个规模收益为零。

## 「游戏性调试」

操作逻辑、美术资产、数值、动画和特效、音乐音效、UI优化

1. 抖动时长偏短，不刺激；→ 调 `ShakeCamera` 的三个时长导出参数（见 [屏幕抖动](50-presentation/screen-shake.md)）
2. 物理碰撞机制检查，取得玩家直觉和游戏性的平衡；
   - 2026-10-13 已知：**撞击的"没劲"有两个原因**——冲量被冻结吞掉（已修，见
     [DESIGN.md](10-turn/DESIGN.md) 的「碰撞冲量晚两步才落地」）+ 被撞的只能飞"剩下的射程"
     （设计取舍，旋钮在 `decel` / `max_charge`）。
3. **蓄力线是否该在"首次撞到棋子"处截断**（2026-10-15 提出，**用户决定先在编辑器里看**）
   - 现状：`player.gd` 的 `_predict_path` **完全忽略其他棋子**（决策 20 的原话：
     "它不预测与其他角色的碰撞"），所以蓄力线会直接**穿过敌人画到墙上** ——
     你瞄一个贴脸的敌人，线从它身上穿过去。
   - 用户原则（2026-10-15）：**这是策略战棋，不是纯台球** —— 撞击前用户对棋子的控制
     应该符合预期；**撞击之后属于高难度操作，不需要预测**。
   - **但直接截断有个代价**（这是没敢直接改的原因）：蓄力条**就是力度读数本身**
     （决策 20：长度 = `蓄力值²/(2·decel)`，末端即落点）。截断之后，满蓄力打贴脸敌人
     和 30% 蓄力长得一模一样，而且"撞飞距离 = 射程 − 已走距离"也读不出来了。
   - 三条路：**① 截断**（最简单，丢力度读数）／**② 全轨迹照画 + 接触点标记**
     （保住读数，要动 `player.tscn` 加一条 Line2D）／**③ 先不动** ← **当前选了 ③**
   - **下一步**：在编辑器里亲眼确认那条线究竟哪里不符合预期，再决定治不治。
     注意**蓄能方式后期不排除改得更简单**，那会改变这里的取舍。
4. 长按蓄力对玩家是一种消耗。本游戏定位为策略性游戏，蓄力条应当是一种确定性的数值操作，而不是考验用户长按的时间——就像围棋一样，落子的力气大不大、声音响不响不应该挑战玩家。之后选择一种更好的方式。
    - 但是碰撞路径对用户应该是一种挑战，棋子轨迹不应计算碰撞棋子之后轨迹变化，而是让玩家自己判断，进行碰撞角度的挑战。
    - 棋子墙壁反弹的轨迹是否提供，需要考虑，原因是轨迹和物理运动规律一般是一致的。当前的物理运动原则是：在没有其他棋子干扰的情况下，蓄力辅助线规划了棋子发射后的路径和到达位置。玩家会依赖反弹来走位，如果不给反弹轨迹，可能导致玩家困惑：「似乎一旦涉及到墙壁，轨迹辅助线就失灵」。不应当给玩家造成这种困惑。

```
关于游戏阳痿
你现在用一个身份干三件事：设计者（决定要什么）、开发者（实现）、玩家（感受）。这三件事抢同一份稀缺资源 —— 新鲜的注意力。开发者知道所有细节，"玩家"就没地方站了。这不是你不够自律，是角色冲突。

四个具体做法：

1. 给"玩"设终点。 每次玩只写三条"作为玩家觉得不对"的话，格式就用「我期待 X，结果是 Y」。不解释、不修、不打开编辑器。攒够 3–5 条再一起改。有了终点，"玩"才不是无限调试。
2. 批量改，别一局一改。 每改一次你就得重新学一遍这游戏 —— 这正是"失去玩家视角"的机制本身。改得越碎、玩得越多，累得越快。
3. 外部玩家是唯一的真解药，你替代不了。而它有两个前提：游戏能给别人跑、别人看得懂。
4. 刻意停几天。 不玩的那几天做不需要玩家视角的活 —— 卡牌设计、文档、game_flow 拆分（TODO 3）。距离会把视角还给你。
```
