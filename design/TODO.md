# 开发过程架构内聚/耦合备忘录

## 用法（2026-10-13 定）

目的是维持工程结构合理、降低模块耦合，避免代码熵增到后期难以理解。

**铁律：每一条待办都必须挂一个「逼它出来的功能」。** 挂不上的就是伪待办，删掉 ——
没有需求在逼的"看起来不优雅"不是债，留着只会让人在错的地方花时间。

起新需求时对一次账（见 [AGENTS.md](../AGENTS.md) 的「熵账本与架构对账」）：
这次逼出了哪条旧债？会不会制造新的中间产物？同一个概念这次碰了几处？

## 「探讨」

1. ~~攻击力/血量显示是否需要整合至 Player 节点~~ —— **已判定：不用做（伪待办，2026-10-13）**。
   数值本身住在 `player.gd`（`atk` / `max_hp` / `role_type`），`hp_overlay` 只是**读**它画字，
   **真相来源只有一个**，不存在双份。而且文档已写明它是调试级、最终会被删掉。
   它的时机是**用户在编辑器里做正式血条**的那天，不是现在。

2. **Player / Mob 是否需要继续抽象合并为同一父类**
   - 现状：**脚本早就合一了** —— `mob.tscn` 挂的就是 `player.gd`，只覆盖 `owner_id = 1`。
   - 剩下的两个真实缺口：(a) `player.gd` 这个名字名不副实（它其实是棋子基类）；
     (b) 两个 `.tscn` 里重复的物理配置。
   - **逼它出来的功能：召唤物**（决策 27）。那是第三种棋子，会真正逼出"三类共用一套物理/表现，
     但生成与寿命不同"。(a) 可以包在任意一个碰到 `.tscn` 引用的 spec 里顺手做。
   - bot 落地时会先复核一次这条：敌方棋子被发射时用的接口必须和玩家一致。

3. **未来可能需要一个回合控制器（controller）作为总线，当前 game_flow 节点只是中间产物**
   - 现状：`game_flow.gd` **754 行 = 全项目 44%**，一个人管 6 件事（阶段机 / 碰撞结算 /
     ZOC 结算 / 碰撞冻结 / 归属方血量 / UI 刷新），"卡牌装载"还留着一个空分节等着塞进去。
   - **逼它出来的功能：卡牌装载（环节 1）。** 那时它会再吃进"出牌 / 装载"两个入口。
   - **做法：不是"先拆再写卡牌"，而是把"拆 game_flow"当成卡牌 spec 的一部分** ——
     这样拆分有明确的验收标准（卡牌装载能不能干净地落进去），而不是无限的。
